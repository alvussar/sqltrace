# sqltrace.sh: ревью и прогон на реальной БД

Стенды (Docker, в облачном контейнере):

| Стенд | Версия | Архитектура |
|---|---|---|
| `doctorkirk/oracle-19c` | Oracle 19.9 EE | non-CDB |
| `gvenzl/oracle-free:23` | Oracle AI Database 26ai Free 23.26.3 | CDB + PDB `FREEPDB1` |

Нагрузка: PL/SQL-цикл в отдельной сессии, ~15–35 exec/s, два курсора: простой `grp = :b1` и `IN (subquery)` с unnesting, чтобы проверить разбор 10053 на запросе с трансформациями.

Файлы: исправленный [sqltrace.sh](sqltrace.sh); оригинал — первый коммит репозитория, найти его: `git log --reverse --oneline -- sqltrace.sh`. `shellcheck` 0.11 чистый.

---

## 1. Анализ: что подтвердилось на БД

| # | Баг | Где | Как проявился | Стенд |
|---|---|---|---|---|
| 1 | **kill -9 / OOM / обрыв без HUP оставляет event включённым на весь инстанс** | `cleanup` (EXIT trap) | Через 15 и 50 с после `kill -9` трейс рос на ~97 KB за 6 с; держится до ручного `off` или рестарта инстанса | 23ai |
| 2 | **`-r 09` отключает порог RATE** | `preflight`: `(( rate > RATE_LIMIT ))` | `09` — ошибка octal, внутри `if (( ))` она даёт false: при 36 exec/s и пороге 9 трейс включился | 23ai, 19c |
| 3 | **10053 для курсора в PDB без `-p`: тихий пустой трейс или ERROR** | `dump_10053` | `v$sql` в CDB$ROOT видит курсоры всех PDB, проверка проходит, а `DUMP_TRACE` из root пишет 39 строк без 10053 при `rc=0` (или файл не создаётся) | 23ai |
| 4 | **10053 с `-p PDB` всегда падает: `трейс 10053 не создан: ''`** | `dump_10053`: путь через `dbms_output` | `DUMP_TRACE` внутри PDB сбрасывает буфер `dbms_output` сессии (пропадает даже `put_line` *до* вызова). Сам трейс создаётся (160 KB) | 23ai (на 19c non-CDB не воспроизводимо, см. риски) |
| 5 | **«Final query after transformations» не финальный** | `extract_10053` | Берётся первый `UNPARSED QUERY IS` (это проверка GPUA/SVS *до* трансформаций). На 19c показан `GRP = ANY (SELECT ...)`, а план — HASH JOIN по unnested `SEL$5DA710D3` | 19c |
| 6 | **Peeked binds всегда пустые** | `extract_10053` | Сразу за строкой `****` идёт пустая строка, и секция закрывается до первого bind | 19c, 23ai |
| 7 | **Повторный захват той же сессии/процесса: SUMMARY молча суммирует старые трейсы** | `collect_10046` | Trace-файл процесса копится всю жизнь сессии; `PARSING IN CURSOR` (единственная строка с `sqlid=`) пишется один раз на курсор, поэтому вырезать «только новое» нельзя: tkprof не свяжет EXEC с курсором | 23ai, 19c |

Найдено чтением кода (детерминированно не воспроизвести):

| # | Баг | Причина |
|---|---|---|
| 8 | Ctrl+C между успешным `alter system set events` и `TRACE_ON=1` оставляет event включённым | `TRACE_ON=1` выставлялся после `sql`; окно — время возврата sqlplus |
| 9 | Отрицательный rate, если курсор вытеснили между замерами | `e2 < e1` → порог проходит всегда |
| 10 | Нет проверки места в `Diag Trace` | event-режим с binds+waits на час может заполнить diag dest |
| 11 | SUMMARY без `current` | LIO = query + current; для DML current существенен |

Наблюдение с БД, не баг скрипта: `alter system set events ... off` доходит до чужой сессии **на границе вызова**. Длинный PL/SQL-вызов (как в тестовой нагрузке) писал трейс ещё 6–10 с после `off`; включение тоже ленивое (с `-d 3` оригинал не нашёл ни одного трейса). В OLTP с короткими вызовами задержка мала.

Что работает корректно в оригинале: валидация входа (инъекции в SQL исключены), `sql_trace[SQL: id]` + `off`, session-режим через `dbms_monitor`, Ctrl+C во время захвата (проверено отправкой INT всей группе процессов, как делает терминал), разбор `total` в tkprof, `umask 077`, отказ от `explain=`.

## 2. Решение (что изменено)

1. **Сторож (dead-man switch)**: перед `alter system` запускается фоновый процесс, который через `SECS + 120 с` выполнит `off` сам. Он игнорирует HUP, а SIGINT фоновым процессам неинтерактивного bash и так игнорируется. При нормальном завершении скрипт его гасит. Если `disable_trace` в cleanup упал, сторож **не** гасится и повторит попытку. `setsid` не используется, потому что в образе 23ai его нет.
2. `TRACE_ON=1` и старт сторожа — **до** `alter system` (повторный `off` безвреден).
3. Числа через `10#`, длина не больше 9 цифр; rate ограничен снизу нулём.
4. Автоопределение PDB по `v$sql.con_id` (в non-CDB `con_id = 0`, ветка не срабатывает). Если курсор есть в нескольких PDB — ошибка с просьбой указать `-p`.
5. Путь к 10053 берётся отдельным `SELECT` из `v$diag_info` после блока, без `dbms_output`. Если в SUMMARY нет плана — WARNING.
6. `extract_10053`: берётся **последний** `Final query after transformations`; в Peeked binds пропускаются ведущие пустые строки; секции выводятся в фиксированном порядке.
7. `warn_stale`: размеры `*.trc` снимаются до включения. Если наш `sqlid` был в файле до захвата — WARNING, что tkprof/SUMMARY учтут прошлый трейс.
8. Свободное место в `Diag Trace` < 2 GB → отказ (с `-f` — только WARNING).
9. `SETTLE_SECS=5` между `off` и сбором файлов.
10. В SUMMARY добавлена колонка `current`.

## 3. Код

Полный файл: [sqltrace.sh](sqltrace.sh). Ключевой фрагмент:

```bash
enable_trace() {
  TRACE_ON=1          # до alter system: окно Ctrl+C закрыто
  start_watchdog
  case $MODE in
    event) sql <<'SQL' >/dev/null
alter system set events 'sql_trace[SQL: @SQL_ID@] wait=true, bind=true, plan_stat=all_executions';
SQL
  ...
}

start_watchdog() {
  local f="$OUT/.watchdog_off.sql"
  { printf '%s\n' 'whenever sqlerror exit failure'; disable_sql; printf '%s\n' 'exit'; } >"$f"
  bash -c 'trap "" HUP; trap "kill \$s 2>/dev/null; exit 0" TERM
           sleep "$1" & s=$!; wait "$s" || exit 0
           "$2" -S -L / as sysdba @"$3"' watchdog \
    "$((SECS + WATCHDOG_GRACE))" "$SQLPLUS" "$f" </dev/null >>"$OUT/.watchdog.log" 2>&1 &
  WATCHDOG_PID=$!
}
```

## 4. Тесты (все на живой БД)

| Сценарий | Оригинал | Исправленный |
|---|---|---|
| event, 15 с, 19c | ✓ 10046; ✗ Final query до трансформаций; ✗ binds пустые | ✓ unnested query совпадает с планом, 2 bind'а |
| event без `-p`, курсор в PDB (23ai) | ✗ 10053 пустой при rc=0 | ✓ «курсор живёт в PDB FREEPDB1», полный 10053 |
| `-n -p FREEPDB1` (23ai) | ✗ `трейс 10053 не создан: ''` | ✓ |
| `-S SID,SERIAL` (19c, 23ai) | ✓ 10046 (10053 без `-p` на 23ai ✗) | ✓ + WARNING о старом трейсе в файле |
| `-r 09` при 15–36 exec/s | ✗ порог обойдён, трейс включён | ✓ отказ «~36 exec/s > порога 9» |
| Ctrl+C на 12-й секции из 60 | ✓ трейс выключен | ✓ трейс выключен, результаты собраны |
| `kill -9` во время захвата | ✗ трейс пишется через 50 с, выключен вручную | ✓ сторож выключил на ~125 с (`System altered.`), рост 0 |
| несуществующий sql_id, `-n` | — | ✓ `ORA-20001 ... not in shared pool`, rc=1 |

Повторить: `docker run -d --shm-size=2g -e ORACLE_SID=ORCLCDB -e ORACLE_PWD=... doctorkirk/oracle-19c` (создание БД ~15 мин), затем под `oracle`: `./sqltrace.sh -s <sql_id> -d 15`.

## 5. Альтернативы

- **Сторож в БД** (`DBMS_SCHEDULER` one-shot job, `off` через `SECS + grace`) переживает и падение хоста с клиентом, если скрипт запускается не на сервере БД. Минус — создаёт объект в БД, на проде это часто требует согласования.
- **Точный SUMMARY при повторном захвате**: склеить заголовок файла + блок `PARSING IN CURSOR ... END OF STMT` нашего курсора из старой части + новые байты. Даёт статистику только за окно, но зависит от того, что номер курсора `#…` не переиспользовали; оставлено как WARNING.
- **ASH/`v$sql_monitor` + `dbms_xplan.display_cursor(format=>'ALLSTATS LAST +PEEKED_BINDS')`** вместо 10046 для частых запросов: нулевой overhead на сессии, но без waits по каждому вызову.
- `p_component => 'Optimizer'` вместо `'Compiler'` — трейс 10053 меньше (без дампа компилятора), если нужен только CBO.

## 6. Риски

- **Event-режим трассирует sql_id во всех сессиях и во всех PDB инстанса** (`alter system` из root). Порог RATE считается по `v$sql.executions` суммарно по всем PDB.
- `max_dump_file_size` (на стендах 32M и unlimited) только предупреждает: на долгом захвате трейс обрежется и tkprof посчитает неполно.
- **Пункт 4 (сброс `dbms_output` в PDB) проверен только на 23ai/26ai**: 19c в доступном образе non-CDB. Исправление от этого не зависит (путь берётся через SELECT), но на вашем 19c CDB стоит один раз прогнать `-n -p <PDB>`.
- Сторож живёт на том же хосте: перезагрузка хоста без рестарта инстанса невозможна, так что это ок; но если `sqlplus / as sysdba` недоступен (например, сломан ORACLE_HOME), не сработает и сторож.
- После `off` сессии с длинными вызовами пишут трейс ещё несколько секунд; `SETTLE_SECS=5` — компромисс.
- Тесты на 19.9 RU и 23.26; поведение `DUMP_TRACE` между RU может отличаться. Скрипт рассчитан на single instance, RAC не поддерживается (как и в оригинале).
- Используются community-образы Oracle с Docker Hub: только для тестов, лицензирование EE на ваше усмотрение.
